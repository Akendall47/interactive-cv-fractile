PYNQZOOM · the algorithm, in hardware

Most of this image is never computed

Background. PYNQZOOM is a team-built fractal explorer. You zoom in the browser, and an FPGA on a PYNQ-Z1 board draws each frame. Its core is this algorithm.

  1. Take a square. Compute only its border.
  2. Border all one colour? Fill the inside, no maths needed.
  3. If not, split into four and repeat. At the smallest size, compute every pixel.

PYNQZOOM · inside the FPGA

48 cores, and the CPU gets out of the way

Background. The board’s chip has an ARM CPU and an FPGA side by side. We put the whole renderer in the FPGA. I helped design it and wrote the software around it.

  1. The CPU sets the view and presses start. The FPGA renders the whole frame by itself.
  2. Two engines take alternate sixteenths. Each has a Mariani–Silver scheduler and 24 cores.
  3. A comparator checks each border: fill, split, or compute every pixel.

PYNQZOOM · the trade-off

More cores, or more precision?

Background. The FPGA has a fixed budget of multipliers and logic. We could spend it on more cores, or on cores that can also do wider maths. We built both.

  1. More cores (dual_core, 48): more pixels at once, so frames arrive faster.
  2. More precision (dual_precision, 32): each core can switch to wide maths, 33 fraction bits instead of 16.
  3. Past about 256× zoom, 16 bits can’t tell neighbouring pixels apart and the image turns to blocks. Only wide mode goes deeper, at roughly a fifth of the speed.
From your job description · SoC & Compute Architect“How physical design constraints feed back into architectural choices” ↗The FPGA’s multiplier budget was fixed, and it forced the choice: 48 narrow cores, or 32 that can switch to wider maths. The right build depends on the zoom. My repo: RTL ↗

PYNQcast · the rendering algorithm

640 rays a frame, and none of them depend on each other

Background. PYNQcast is a team-built multiplayer game. Each PYNQ-Z1 board draws a first-person 3D view in its FPGA, 640 × 480 at about 60 fps, Wolfenstein-style.

  1. For each screen column, cast one ray from the player.
  2. Step it across the map one grid line at a time (DDA). Lookup tables replace the divides.
  3. The distance to the first wall sets that column’s wall height.
From your job description · Compute Architect“AI acceleration/vector-matrix compute” ↗A frame is 640 independent lanes of the same arithmetic, the shape accelerators are built for. Lookup tables replace the divides, because dividers cost area and cycles. Team repo: raycaster RTL ↗

PYNQcast · I led the server

Never let slow work block fast work

Background. The boards play together through a server I built on AWS. It runs the game 60 times a second, sends every board the state, and saves results.

  1. Receive, tick, send: three stages joined by queues.
  2. Slow database writes get their own thread.
  3. They’re batched: one round-trip per tick.
From your job description · System Architect“Comfortable working across disciplines — hardware, firmware, and software” ↗One project, three layers: FPGA RTL, board software and an AWS server. I measured each: ~50 µs receive, ~10 µs unpack, ~300 µs to the FPGA, 20–50 ms of network. My repo: server ↗

RISC-V CPU · I wrote the cache

A cache only helps if the pipeline waits for it correctly

Background. A team of four built a working RISC-V processor from scratch in SystemVerilog at Imperial. It runs real programs. My part was the data cache.

  1. Hit: data back in one cycle.
  2. Miss: stall the pipeline in the same cycle, fetch the line.
  3. Dirty line: write it back first.
